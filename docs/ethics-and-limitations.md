# Ethics, Limitations & Responsible Use

EduIntel predicts risk about **people**. It is designed as decision **support**
for instructors, never an automated decision-maker.

## Design commitments

- **No automated decisions.** The system recommends; humans decide. Every risk
  view and recommendation states that it supports, not replaces, instructor
  judgement.
- **Association, not causation.** Explanations use language like "associated
  with" and never "caused by". SHAP attributions describe the model, not the
  world. Intervention effectiveness is explicitly labelled observational, with a
  caveat that it does not establish causal effect (no control group; possible
  regression to the mean).
- **Prediction, not fate.** The UI and API say "the model estimates a high risk
  based on observed patterns," never "this student will fail."
- **Uncertainty is surfaced.** Probabilities are calibrated and reported;
  confidence intervals accompany cross-validation; the analyst declines when
  evidence is insufficient rather than guessing.

## Limitations

- **Synthetic data.** The shipped dataset is generated by a documented
  latent-variable model. Relationships are realistic *by construction*; real
  cohorts differ, and real accuracy would be lower and noisier.
- **Proxy labels.** Feedback-method comparison uses star ratings as proxy
  ground truth for sentiment, which is imperfect.
- **Single-term framing.** The demo trains and evaluates on one term; a
  production system should train on past cohorts and predict the current one.
- **Offline fallbacks.** Without an LLM key or transformer weights, the analyst
  and NLP degrade to extractive/rule methods; retrieval quality is lower with the
  hashing-embedding fallback than with real sentence-transformers embeddings.

## Bias risks

- Features like prior GPA and attendance can encode socio-economic factors;
  monitoring for disparate impact across student subgroups is essential before
  any real deployment.
- A model that over-flags a subgroup could concentrate scarce intervention
  resources unfairly. The intervention-aware objective mitigates *missed* high
  risk but does not by itself address fairness across groups.

## Privacy & security

- **Synthetic by default**; student records are minimized (no sensitive
  attributes are modelled).
- **No secrets in source** — configuration via environment variables; `.env` is
  gitignored.
- **Authentication-ready** — an API-key gate and role hooks are built in; a real
  deployment would wire these to institutional identity and access controls.
- **Audit-friendly** — a structured audit log table and JSON request logging are
  provided.
- A production deployment handling real student data would require appropriate
  institutional privacy and compliance controls (e.g. FERPA/GDPR as applicable),
  data-retention policies, and access governance.

## Recommended guardrails for real deployment

1. Keep a human in the loop for every high-stakes action.
2. Monitor calibration and subgroup performance continuously.
3. Re-train on historical cohorts; validate chronologically.
4. Provide students transparency and a route to contest a flag.
5. Treat intervention effectiveness as hypothesis-generating until validated
   with a randomised or matched design.
